## How do we know it works?

Success for the Process layer is defined by **"Zero Rework from Skipped Stages."** If a project must be restarted or significant files must be rewritten because a foundational stage (like the spec or the plan) was bypassed, the process has failed. Conversely, if the build proceeds linearly through the 5 phases without the need to "go back and fix the foundation," the process has succeeded. Success is a "Smooth, Forward-Moving Build."

Another success criterion is **"Economic Cascade Compliance."** The system should consistently use the appropriate model for each task as defined in the cascade. If the system is using expensive "Pro" models for routine directory creation, or if it is failing to switch to "Flash" models when rate-limited, the process is not performing its resource-management function. Success is "Optimal Compute Utilization."

Finally, success is measured by **"Process Observability."** Any stakeholder should be able to look at the `CASESTUDY.md` and the file tree and instantly understand which stage of the process the system is currently in. If the "Stage of Progress" is ambiguous, the process has achieved poor results. Success is a system where the "Map and the Territory" are in perfect alignment.
